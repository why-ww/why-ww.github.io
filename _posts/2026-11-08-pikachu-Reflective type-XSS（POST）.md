# Pikachu Lab - 反射型 XSS（POST）

## 实验模块

模块：XSS

场景：反射型 XSS（POST）

## 漏洞场景

题目名称：反射型 XSS（POST）；平台：Pikachu；方向：Web。

## 测试过程

<br>1. 打开 Pikachu 靶场，进入 XSS 模块下的「反射型 XSS（POST）」。页面首先要求输入用户名和密码，使用靶场账号登录后进入实际的漏洞测试页面。
<br>2. 在页面提供的输入框中输入测试代码 \<script\>alert(1)\</script\>，提交后浏览器弹出了内容为 1 的提示框。
<br>3. 观察浏览器的执行结果，可以确认输入的 JavaScript 代码成功执行，而不是作为普通文本显示；据此判断提交的数据在返回页面时没有得到正确的安全处理，存在反射型 XSS 漏洞。
<br>4. 本题使用 POST 方式提交数据。与 GET 请求不同，POST 请求的数据通常放在 HTTP 请求体中，而不是直接显示在 URL 参数中，因此测试时需要关注 POST 请求提交的参数以及服务器返回的响应内容。

## 分析与解答

### 1.

<br>问题：为什么提交 \<script\>alert(1)\</script\> 后会出现弹窗？
<br>解答：当应用把提交内容反射到 HTML 响应中且未进行上下文相关的输出编码时，浏览器会把其中的 \<script\> 当作页面脚本解析并执行。POST 只是改变参数传输位置，并不会自动消除 XSS 风险。

### 2.

<br>问题：POST 型反射 XSS 与 GET 型在测试关注点上有什么差异？
<br>解答：GET 型参数通常出现在 URL 查询字符串中，而 POST 型参数位于请求体。测试时除了构造提交内容，还要观察 POST 参数是否被服务器原样反射到响应页面；无论参数位置如何，只要响应中缺少安全编码，就可能形成反射型 XSS。

### 3.

<br>问题：看到弹窗后应如何理解这个验证结果？
<br>解答：alert 弹窗表明 JavaScript 被执行，而不是作为普通文本展示，这是 XSS 的典型验证信号。它只能说明该输入点存在脚本注入条件，实际影响仍需结合响应上下文、触发方式和受害者的交互路径进一步判断。


## 漏洞原理与修复思路




<br>反射型 XSS 的核心是应用接收用户输入并将其嵌入返回页面，但没有按 HTML、属性、JavaScript 或 URL 等上下文进行正确编码，导致浏览器把输入内容当作代码解析。本题目使用 POST 提交，说明参数放在请求体中同样可能被反射并触发脚本执行，请求方法本身不是防护措施。

<br>修复时应优先采用上下文相关的输出编码，确保用户输入在 HTML、属性、脚本等位置只作为数据处理；同时可结合输入校验、模板引擎自动转义、内容安全策略（CSP）以及 HttpOnly Cookie 等纵深防御措施。仅依赖 POST 提交、前端过滤或简单替换危险字符通常不足以彻底消除 XSS。


## 学习总结

本次靶场实验主要学习了：

<br>1. 本实验以 alert(1) 弹窗作为 JavaScript 成功执行的验证信号，并说明反射型 XSS 不只存在于 GET 参数中。POST 请求的数据位于请求体，仍然需要检查服务器是否将提交内容不安全地反射到响应页面。
<br>2. 后续学习应重点掌握输出编码的上下文差异、POST 请求的抓包与重放方法，以及 CSP、HttpOnly、模板自动转义等防护机制，避免把“使用 POST”误认为安全边界。
