# Pikachu Lab - 存储型xss

## 实验模块

模块：XSS

场景：存储型xss

## 漏洞场景

题目名称：存储型xss；平台：Pikachu；方向：Web。

## 测试过程

<br>1. 在留言框中输入测试 Payload：\<script\>alert(1)\</script\>，随后点击 submit 提交留言。
<br>2. 提交后，浏览器成功弹出内容为 1 的提示框，说明输入的 JavaScript 代码被浏览器执行，而不是作为普通文本显示。
<br>3. 关闭弹窗后刷新当前页面，浏览器再次弹出 1，说明提交内容没有随页面刷新消失，而是被保存下来，并在页面重新加载时再次执行，由此验证存在存储型 XSS 漏洞。

## 分析与解答

### 1.

<br>问题：为什么刷新页面后仍然会弹出提示框？
<br>解答：这符合存储型 XSS 的特征。提交的脚本内容被保存后，在页面重新加载时再次被输出到 HTML 中，并被浏览器当作脚本执行，因此弹窗会重复出现。

### 2.

<br>问题：存储型 XSS 与反射型 XSS 的主要区别是什么？
<br>解答：存储型 XSS 的恶意内容会被保存，并在后续访问同一页面时再次触发；反射型 XSS 通常只在单次请求的响应中立即反射并执行，不会因为刷新同一页面而自动再次触发。

### 3.

<br>问题：alert(1) 弹窗验证了什么？
<br>解答：弹窗说明提交内容进入了页面上下文，并被浏览器作为 JavaScript 执行，而不是仅作为文本显示；刷新后仍弹窗则进一步说明该内容具有持久化特征。


## 漏洞原理与修复思路

<br>存储型 XSS 的典型原理是：用户提交的内容被服务端保存，之后在页面中被输出时没有按照 HTML 上下文进行安全编码或过滤，浏览器将其中构造的标签或脚本解析并执行。本题中提交 \<script\>alert(1)\</script\> 后出现弹窗，刷新后仍再次执行，符合这一原理。

<br>修复存储型 XSS 时，重点是在输出点根据 HTML、属性、URL 或 JavaScript 等不同上下文进行编码，必要时对允许的 HTML 使用可靠的白名单清洗；同时可结合输入校验、内容安全策略等措施降低脚本执行风险。仅依赖前端过滤不能替代服务端输出编码。


## 学习总结

本次靶场实验主要学习了：

<br>1. 验证存储型 XSS 时，可以先提交可观察的脚本 Payload，确认浏览器是否执行，再刷新页面观察 Payload 是否持续触发，从而区分一次性反射与持久化存储。
<br>2. 本题的核心风险在于用户输入被保存并在后续页面加载时重新输出，且浏览器将其当作脚本执行；理解“存储—输出—执行”的链路有助于分析同类 XSS 漏洞。
<br>3. 后续学习可重点关注不同输出上下文下的编码方式、HTML 清洗策略以及内容安全策略的作用，避免只从单一 Payload 角度理解 XSS。
