# Pikachu Lab - 存储型 XSS

## 实验模块

模块：XSS

场景：存储型 XSS

## 漏洞场景

题目名称：存储型 XSS；平台：Pikachu；方向：Web。

完成状态依据旧稿中保留的提交、首次弹窗和刷新后再次弹窗记录；本次整理没有新增留言或删除数据库记录。源码复核对象为 `vul/xss/xss_stored.php`。

## 测试过程

<br>1. 既有记录在留言框中提交 `<script>alert(1)</script>`，提交后浏览器出现内容为 `1` 的对话框。
<br>2. 关闭弹窗并刷新页面后，对话框再次出现。这个现象说明测试内容不是只存在于一次响应中，而是已经被保存，并在后续读取留言列表时再次输出。
<br>3. 当前源码先用 `escape($link, $_POST['message'])` 处理输入，再执行 `insert into message(content,time) values(...)`。这里的转义服务于 SQL 字符串，并不等于 HTML 输出编码。
<br>4. 页面随后执行 `select * from message`，遍历每条记录，并把 `$data['content']` 直接拼进 `<p class='con'>...</p>`。读取阶段没有 HTML 编码，因此数据库中的标签会被浏览器解析。

## 源码数据流

<br>1. 来源（source）：POST 表单中的 `message`。
<br>2. 存储：输入经过数据库转义后写入 `message.content`；该处理主要降低 SQL 语法被破坏的风险，并不会把 HTML 标签变成安全文本。
<br>3. 读取：页面查询 `message` 表的全部留言。
<br>4. 输出点（sink）：`$data['content']` 被直接写入 `<p>` 标签正文，形成“提交—入库—读取—执行”的持久化链路。

## 验证观察点与常见问题

<br>1. 区分存储型与反射型的关键观察点是：关闭或刷新后，内容是否仍能从服务器数据中重新出现并触发。
<br>2. `mysqli_real_escape_string` 一类数据库转义只针对 SQL 上下文，不能代替 HTML 编码；安全措施必须匹配最终输出上下文。
<br>3. 留言提交后若每次打开页面都触发，清理测试数据前应先禁用脚本或使用安全方式处理，避免反复执行。本文没有新增或删除记录。
<br>4. 同一页面的删除参数还存在独立的 SQL 拼接逻辑，但它不是本篇 XSS 验证范围，不应混为一个漏洞结论。

## 分析与解答

### 1. 为什么刷新后仍会触发？

因为测试内容已保存到数据库。刷新时页面重新查询并输出该记录，浏览器再次解析其中的脚本，所以触发不依赖原始提交请求。

### 2. 为什么数据库转义没有阻止 XSS？

数据库转义处理的是引号等 SQL 特殊字符，目标是让数据安全进入 SQL 字符串；XSS 发生在数据离开数据库并进入 HTML 时。两个上下文不同，需要不同的编码方式。

### 3. 应该怎样修复？

读取留言并输出到 HTML 文本节点时，应进行 HTML 实体编码。若业务确实允许部分富文本，应使用成熟的 HTML 白名单清洗器，只保留明确允许的标签和属性；同时配合 CSP，并为会话 Cookie 设置合适的安全属性。

## 学习总结

<br>1. 本题已经实际验证，核心链路是 `POST message → 数据库存储 → 查询留言 → 未编码输出 → 后续访问者浏览器执行`。
<br>2. 判断存储型 XSS 要观察持久化行为，而不是只看一次提交后的弹窗。
<br>3. 数据库安全处理与浏览器输出安全处理不能互相替代。
