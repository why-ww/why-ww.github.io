# Pikachu Lab - SSRF（cURL）

## 实验模块

模块：SSRF

场景：SSRF（cURL）

## 漏洞场景

题目名称：SSRF（cURL）；平台：Pikachu；方向：Web。

实验状态：原理分析。已核对 Pikachu 当前源码中的 ssrf\_curl.php，但没有修改 url 参数发起服务端请求，也没有探测本机端口或内网地址。以下内容是隔离靶场中的建议验证步骤。

## 测试过程

<br>1. 当前入口为 /pikachu/vul/ssrf/ssrf\_curl.php。页面自带链接把 url 参数设置为当前部署路径下的 http://127.0.0.1/.../vul/ssrf/ssrf\_info/info1.php，用来让 Pikachu 服务器读取一首诗。
<br>2. 源码读取 $URL=$\_GET['url']，随后依次执行 curl\_init($URL) 与 curl\_exec($CH)。参数没有经过协议白名单、主机解析或内网地址检查，因此请求由服务器发出，而不是由访问页面的浏览器直接发出。
<br>3. 建议先点击项目自带链接建立安全基线。若响应出现 info1.php 的内容，说明服务端 cURL 能访问回环地址。然后可把 url 改为同一隔离网络中自己控制的 HTTP 标记页，并检查该服务的访问日志是否记录了来自 Pikachu 容器的请求。
<br>4. 当前代码没有设置 CURLOPT\_RETURNTRANSFER，curl\_exec() 会直接把响应体写入当前输出；其返回值通常是成功或失败状态，随后 echo $RES 还可能在正文后附加 1。这个现象不代表目标页面本身含有数字 1。
<br>5. 验证到“服务端能访问受控页面”即可停止，不应扫描真实内网端口、访问云元数据地址或读取系统文件。本篇没有实际访问任何目标，所以只记录源码数据流和建议方法。

## 其他观察

源码关闭了 TLS 证书校验：CURLOPT\_SSL\_VERIFYPEER 被设置为 FALSE，这会额外削弱 HTTPS 请求的身份验证。cURL 支持的协议由编译选项决定，不能只依据注释假设所有协议都可用；应以 curl\_version() 或当前容器实际配置为准。即便只开放 HTTP/HTTPS，回环、内网和链路本地地址仍可能造成 SSRF。


## 分析与解答

### 1.

<br>问题：浏览器也能访问 URL，为什么这里叫服务端请求伪造？
<br>解答：真正发起连接的是运行 PHP 的服务器进程。它拥有与访问者浏览器不同的网络位置和权限，可能访问只对容器、主机或内网开放的服务。

### 2.

<br>问题：只允许 http 和 https 就能修复 SSRF 吗？
<br>解答：不能。协议白名单可以阻止 file、gopher 等非预期协议，但 HTTP 仍能指向 127.0.0.1、私有网段、链路本地地址或经 DNS 重绑定后的内部目标。

### 3.

<br>问题：为什么要关闭自动重定向或校验每一跳？
<br>解答：外部白名单地址可能返回 3xx 并把服务器引向内部地址。如果只验证最初 URL，而请求库自动跟随新位置，仍然可能绕过目标限制。


## 漏洞原理与修复思路

<br>核心数据流是 GET 参数 url → curl\_init() → curl\_exec() → 目标响应进入当前页面。攻击者控制服务端请求的目的地址，利用的是服务器自身的网络可达性与身份环境，而源码又把响应直接返回给客户端，形成有回显 SSRF。

<br>修复时应优先使用业务目标白名单，而不是接收完整 URL。必须接收 URL 时，只允许 HTTP/HTTPS，规范化并解析主机，解析所有 A/AAAA 记录，拒绝回环、私有、链路本地、保留和其他内部地址；禁用重定向或逐跳重新校验。生产环境还应通过出站代理或防火墙限制访问范围，设置连接与响应超时、大小上限，恢复 TLS 证书校验，并避免把后端原始响应直接返回给用户。


## 学习总结

本次靶场实验主要学习了：

<br>1. SSRF 的关键是用户控制目标，而连接由服务器使用 cURL 发出。
<br>2. 当前源码对 url 不做校验并直接执行请求，但本篇尚未访问项目自带或自建标记页。
<br>3. 防护需要同时覆盖协议、解析后的 IP、重定向、出站网络和响应处理，不能只做字符串过滤。
