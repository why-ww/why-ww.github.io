# CTFHub Writeup - vim缓存

## 题目类型

Web

## 题目描述

<br>当开发人员在线上环境中使用 vim 编辑器，在使用过程中会留下 vim 编辑器缓存，当vim异常退出时，缓存会一直留在服务器上，引起网站源码泄露。
<br>备份文件下载 - vim
<br>flag 在 index.php 源码中

## 解题过程

<br>1. 根据 Vim 编辑 PHP 文件时常见的交换文件命名规则，访问了目标路径 /.index.php.swp，并获得了一个名为 \`index.php.swp\` 的文件。
<br>2. 获得文件后发现无法直接打开，并先将其放在 D盘中。
<br>3. 直接使用 curl 查看交换文件时，输出中出现了页面提示、// ctfhub\{xxxx\} 和 \<?php 等内容，但同时提示 \`Binary output can mess up your terminal\`，因此无法直接在终端中正常查看。
<br>4. 进入 Linux 系统后使用 vim -r .index.php.swp 恢复源码，看到 // ctfhub\{xxxx\}，但将该内容作为 flag 提交后发现错误。
<br>5. 随后执行 curl URL/.index.php.swp \| strings \| grep "\\$"，从交换文件中的变量相关内容中找到了正确 flag。

## 疑问与解答

### 1.

<br>为什么访问 index.php 看不到源码？
<br>正常访问 PHP 文件时，Web服务器通常会交给 PHP解释器执行，返回执行结果而不是源代码；而 Vim交换文件可能被服务器当作静态文件直接返回，因此会造成源码泄露。

<br>

### <br>2.

<br>为什么直接用 curl 输出交换文件会出现二进制终端提示？
<br>.swp 是 Vim 的二进制交换文件，直接输出可能包含控制字符并污染终端。使用 strings 可以提取其中连续可读的字符串，便于定位源码片段和变量内容。

<br>

### <br>3.

<br>为什么 vim -r 中看到的 // ctfhub\{xxxx\}不是正确答案？
<br>该内容可能只是注释、缓存中的诱饵或不完整片段；结合后续通过 $相关字符串找到正确 flag 的记录，推测真正答案或许位于源码变量赋值等内容中。


## 本题的核心逻辑：



<br>Vim 编辑 index.php 时可能在同目录生成隐藏交换文件，常见名称为 .index.php.swp。如果服务器没有禁止访问这类临时文件，攻击者就可能直接下载交换文件并从中恢复编辑中的 PHP 源码。

<br>题目的关键在于区分正常 PHP 页面和编辑器缓存：正常请求 index.php 得到的是 PHP 执行结果，而访问遗留的 .swp 文件可能得到包含源码和变量数据的静态内容。交换文件是二进制格式，因此可以结合 Vim 恢复功能或 \`strings\` 提取可读字符串。

<br>本题的源码泄露疑似源于线上环境未清理 Vim 异常退出后留下的交换文件，并且 Web 服务仍允许访问该隐藏文件；因此推测敏感源码和 flag 被间接暴露。


## 笔记

这道题主要学习了：

<br>1. 遇到源码无法直接查看的 Web题目时，应关注编辑器缓存、备份文件和临时文件等非正常资源。Vim交换文件常见形式为 .原文件名.swp，可能保存编辑中的源码内容。
<br>2. .swp 属于二进制文件，直接使用 curl 输出可能触发终端保护；strings 能提取其中的可读字符串，并配合关键词或变量符号定位源码片段。
<br>3. 恢复工具显示的注释或示例字符串不能直接视为最终 flag，应结合源码结构、变量赋值和输出逻辑进行核实。
