# Pikachu Lab - 数字型注入

## 实验模块

模块：SQL注入

场景：数字型注入

## 漏洞场景

题目名称：数字型注入；平台：Pikachu；方向：Web。

## 测试过程

<br>1. 进入 Pikachu 的 SQL-Injection → 数字型注入（POST）页面，选择用户 ID 为 4 并点击查询，页面正常返回 Allen 的用户信息。
<br>2. 使用 Burp Suite 的 Proxy 抓取该查询请求并发送到 Repeater；请求为 POST /pikachu/vul/sqli/sqli\_id.php，Content-Type 为 application/x-www-form-urlencoded，请求体包含 id=4&submit=查询，确认用户选择的 ID 通过 id 参数提交。
<br>3. 在 Repeater 中修改请求体中的 id 参数，先发送 id=4 AND 1=1（URL 编码为 id=4%20AND%201=1），再发送 id=4 AND 2=1（URL 编码为 id=4%20AND%202=1），用于对比恒真与恒假条件对原始查询结果的影响。
<br>4. 继续将参数改为 id=4 OR 1=1（URL 编码为 id=4%20OR%201=1）并点击 Send，响应中出现了 vince、allen、kobe、grady、kevin、lucy、lili 等多个用户的信息；与正常查询只返回一个用户相比，结果发生明显变化，说明注入的 OR 条件使原本不满足 ID 条件的记录也被查询出来。

## 分析与解答

### 1.

<br>问题：为什么 id=4 OR 1=1 会让响应中出现多个用户？
<br>解答：在 SQL 的 WHERE 条件中，OR 只要有一侧为真，整体就可能为真；1=1 恒为真，因此原查询条件被整体放宽，满足条件的记录不再局限于 id=4，响应中便可能出现多个用户。

### 2.

<br>问题：AND 1=1 与 AND 2=1 的对比测试有什么意义？
<br>解答：AND 1=1 是恒真条件，通常不改变原查询的筛选逻辑；AND 2=1 是恒假条件，通常会使 WHERE 条件不成立。通过对比两者，可以观察布尔条件是否影响查询结果，从而辅助判断参数是否被带入 SQL 语句。

### 3.

<br>问题：数字型注入与字符型注入在构造测试参数时有什么区别？
<br>解答：数字型注入通常出现在数值参数直接进入 SQL 的位置，一般不需要引号闭合；字符型注入通常位于字符串常量中，往往需要处理引号闭合和注释。本题通过 POST 请求体中的 id 参数测试布尔条件，符合数字型注入的测试思路。


## 漏洞原理与修复思路

<br>SQL 注入的本质是应用程序把外部输入当作 SQL 代码的一部分执行，导致攻击者能够改变原查询的条件或结构。本题中 id 参数被用于数值查询，追加 OR 1=1 后 WHERE 子句的真值被改变，因此返回结果从单个用户扩展为多个用户。

<br>推测后端查询可能将 POST 请求中的 id 直接拼接到类似 WHERE id = $id 的数值上下文，因而无需引号闭合即可插入 AND 或 OR 条件；OR 1=1 使条件恒真，从而扩大了结果集。

<br>修复时应使用参数化查询或预编译语句，将 id 作为参数绑定而不是拼接进 SQL；同时对输入做严格的类型校验，只接受合法整数，并结合最小权限数据库账户、错误信息隐藏和统一日志审计降低注入风险。POST 提交本身并不能防止 SQL 注入。


## 学习总结

本次靶场实验主要学习了：

<br>1. 数字型注入的识别要点是参数作为数值使用、通常不需要引号闭合，布尔条件可以直接改变 WHERE 子句的真假；恒真条件可能扩大结果集，恒假条件可能使结果为空。
<br>2. Burp Suite Repeater 适合对同一请求反复修改参数并对比响应；抓包时应先确认参数位于 URL 还是请求体，以及请求方法和 Content-Type，再构造测试 payload。
<br>3. 后续学习应重点掌握参数化查询与输入类型校验，并理解布尔逻辑、联合查询、盲注等手法与数字型注入之间的关系，形成从验证注入点到修复漏洞的完整认识。
