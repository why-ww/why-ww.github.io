# Pikachu Lab - 基于表单的暴力破解

## 测试过程

<br>1. 打开 Pikachu 的“基于表单的暴力破解”页面，输入测试账号密码 admin / 123456。
<br>2. 配置 SwitchyOmega，将代理设置为 127.0.0.1:8080，并使用 \<-loopback\> 让 localhost 流量经过 Burp。
<br>3. 在 Burp 中成功抓到登录 POST 请求，确认参数为 username=admin&password=123456&submit=Login。
<br>4. 将请求发送到 Intruder，选择 Sniper 模式，只把密码值设为 Payload 位置。
<br>5. 添加多个候选密码并启动攻击。
<br>6. 对比响应长度，发现 123456 的响应长度明显不同。
<br>7. 查看响应正文并重新登录，确认正确凭据为 admin / 123456。

## 其他观察

123456 的响应长度明显不同，可能源于登录成功页面与失败提示在正文内容或页面结构上存在差异，因此响应长度可以作为筛选候选密码的线索。


## 分析与解答

### 1.

<br>问题：为什么访问本地 localhost 时要在代理绕过规则中配置 \<-loopback\>？
<br>解答：浏览器或代理扩展通常会对 localhost/127.0.0.1 启用绕过，避免本地回环流量进入代理；\<-loopback\> 的作用是取消这一绕过，使本地靶场请求能够被 Burp 捕获。

### 2.

<br>问题：Sniper 模式只标记密码位置适合什么场景？
<br>解答：Sniper 每次只替换一个 Payload 位置，适合已知用户名、仅需枚举密码的场景；本题保持 username=admin 不变，仅对 password 进行替换，与该模式的使用方式一致。

### 3.

<br>问题：暴力破解时为什么可以关注响应长度？
<br>解答：登录成功和失败通常返回不同页面或提示，正文长度可能随之变化。Intruder 的结果表可按长度排序或比较，异常长度可作为候选结果；但长度差异只是线索，还应查看响应正文并重新登录验证。


## 漏洞原理与修复思路



<br>基于表单的暴力破解本质是攻击者自动化提交大量账号密码组合，利用应用缺少频率限制、验证码、失败锁定或强密码策略等防护，持续猜测登录凭据。登录成功与失败响应存在差异时，也会降低猜测结果的判定成本。

<br>修复时应综合采用登录频率限制与临时封禁、验证码或人机校验、失败次数锁定、强密码策略和多因素认证；同时统一登录失败提示，避免通过响应正文或长度差异泄露账号或密码是否正确。


## 学习总结

本次靶场实验主要学习了：

<br>1. 本题通过浏览器代理配置将本地表单登录请求交给 Burp，再在 Intruder 中固定用户名、仅替换密码，完整体现了表单暴力破解的基本流程：抓包、定位参数、设置 Payload 位置、发起枚举和筛选结果。
<br>2. 响应长度可以作为结果筛选信号，但不能只依赖长度下结论；查看响应正文并重新登录验证，能够减少误判。这也说明登录接口应避免在成功与失败时返回明显可区分的内容。
<br>3. 后续学习可围绕口令字典组织、不同 Intruder 攻击模式的适用条件，以及频率限制、验证码、账户锁定等防护的绕过与检测展开，从而更系统地理解暴力破解的利用条件和修复重点。
