# Pikachu Lab - 代码执行

## 实验模块

模块：RCE

场景：代码执行

## 漏洞场景

题目名称：代码执行；平台：Pikachu；方向：Web。

实验状态：原理分析。已核对 Pikachu 当前源码中的 rce\_eval.php，但没有向本地靶场提交 PHP 代码，也没有记录页面输出。以下内容是隔离靶场中的建议验证步骤。

## 测试过程

<br>1. 当前入口为 /pikachu/vul/rce/rce\_eval.php，页面通过 POST 提交字符串，参数名为 txt，提交按钮参数名为 submit。
<br>2. 源码在确认 submit 存在且 txt 非空后，直接执行 @!eval($\_POST['txt'])。输入没有经过允许列表解析，也没有被当作普通文本输出，而是被 PHP 解释器当成代码执行。
<br>3. 建议先提交普通字符串观察基线，再把请求发送到 Burp Repeater。在本地隔离靶场中可使用无破坏性的标记代码 echo "RCE\_TEST";，对应请求体可写为 txt=echo%20%22RCE\_TEST%22%3B&submit=提交。
<br>4. 按源码推导，eval() 会执行 echo 并把 RCE\_TEST 写入响应。由于 echo 语句本身不会让 eval() 返回 true，页面还可能继续追加“你喜欢的字符还挺奇怪的!”；这个提示来自外层 @!eval(...) 判断，不代表标记代码没有执行。
<br>5. 验证时应确认响应中出现的是由提交代码产生的独立标记，并检查 PHP 语句是否以分号结束。@ 只会抑制部分错误显示，不会阻止 eval() 执行。本篇没有实际发送请求，因此不记录成功结果。

## 其他观察

“命令执行”和“代码执行”不是同一条数据流：前一题把输入交给操作系统 Shell，本题把输入交给 PHP 的 eval()。两者都可能导致 RCE，但 Payload 语法、执行环境和防护方式不同。常见失败原因是遗漏 PHP 语句末尾的分号、引号在表单编码中被改变，或只看到页面固定提示就误判为没有执行。


## 分析与解答

### 1.

<br>问题：为什么输入 echo "RCE\_TEST"; 可以验证代码执行？
<br>解答：echo 是 PHP 语句。如果响应出现由该语句生成的标记，说明 txt 的内容不是作为普通字符串处理，而是进入了 PHP 解释执行流程。

### 2.

<br>问题：@ 符号是否能阻止恶意代码运行？
<br>解答：不能。@ 主要用于抑制错误信息显示，eval() 仍会解释并执行传入代码。隐藏报错只会降低可见性，不会消除漏洞。

### 3.

<br>问题：为什么页面可能同时出现 RCE\_TEST 和固定提示？
<br>解答：echo 会直接产生输出，但通常不会让 eval() 返回 true；外层 !eval(...) 条件因此仍可能成立，程序随后追加固定提示。判断漏洞应关注标记是否执行，而不是只看提示文字。


## 漏洞原理与修复思路

<br>核心数据流是 POST 参数 txt → eval() → PHP 解释器。eval() 把字符串提升为可执行代码，用户因此可以调用当前 PHP 进程权限范围内的函数，风险通常远高于普通输入错误。

<br>修复的首选方案是删除 eval()，把业务需求改写为固定操作或明确的允许列表映射，例如把有限的选项映射到预定义函数。不要尝试仅靠删除括号、分号或关键字过滤 PHP 语法；这种黑名单容易被编码和语法变体绕过。生产环境还应使用最小权限、禁用不需要的危险函数，并避免向用户显示详细错误。


## 学习总结

本次靶场实验主要学习了：

<br>1. 代码执行的关键是用户字符串被 eval() 交给语言解释器。
<br>2. 当前源码确认 txt 被直接执行，但本篇尚未实际提交 PHP 代码。
<br>3. 正确修复方式是移除动态代码执行，用固定功能或允许列表完成业务需求。
