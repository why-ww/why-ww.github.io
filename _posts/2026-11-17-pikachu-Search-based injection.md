# Pikachu Lab - 搜索型注入

## 实验模块

模块：SQL注入

场景：搜索型注入

## 漏洞场景

题目名称：搜索型注入；平台：Pikachu；方向：Web。

## 测试过程

<br>1. 首先在搜索框输入 allen，页面正常返回 username: allen、uid: 2、email: allen@pikachu.com，说明页面可以根据输入的用户名查询数据库中的用户信息。
<br>2. 打开浏览器开发者工具进入 Network 选项卡，输入用户名并点击搜索后，定位到请求 /pikachu/vul/sqli/sqli\_search.php。该功能使用 GET 请求，搜索内容通过 name 参数传递，随后请求被发送到 Burp Suite Repeater 以便修改参数并观察响应。
<br>3. 在 Burp Repeater 中将 name 参数修改为 %' OR '1'='1' \# 并发送请求，页面返回了多个用户的信息，包括 Vince、allen、Kobe、Grady 等。与正常搜索只返回一个用户相比，查询返回多条记录，说明输入内容改变了后台 SQL 查询逻辑，验证了搜索型 SQL 注入。

## 其他观察

记录中分析了该注入涉及的三个组成部分：% 是 LIKE 模糊查询中的通配符，可匹配任意长度字符；OR '1'='1' 用于构造恒真条件；\# 是 MySQL 注释符，用于注释后续 SQL 内容。其中 % 负责扩大模糊匹配范围，OR '1'='1' 改变原本的查询判断逻辑，最终使服务器返回当前查询涉及的多条用户记录。


## 分析与解答

### 1.

<br>问题：正常搜索 allen 时只返回一个用户，而输入 %' OR '1'='1' \# 后返回多条记录，说明了什么？
<br>解答：这说明输入可能被拼接进 SQL 查询条件，OR '1'='1' 使条件恒真，\# 注释后续语法，% 配合 LIKE 扩大匹配范围，因此结果集从单个用户扩展为多条用户记录；具体拼接形式仍需结合源码确认。

### 2.

<br>问题：在搜索型注入中，为什么要关注 LIKE 的通配符 %？
<br>解答：搜索功能常使用 LIKE 进行模糊匹配，若查询形如 LIKE '%输入%'，输入的 % 可以匹配任意长度字符串，再配合引号闭合和恒真条件，可能改变 WHERE 子句的判断逻辑并返回更多记录。该解释属于原理分析，实际 SQL 语句应以源码为准。


## 漏洞原理与修复思路

<br>搜索型 SQL 注入的成因是将搜索关键字直接拼接到 SQL 查询中，尤其是 LIKE 模糊查询场景。输入中的引号可能闭合原字符串，OR 可构造恒真条件，\# 可注释剩余 SQL，LIKE 通配符 % 可扩大匹配范围，从而改变查询逻辑并返回非预期数据。

<br>修复时应使用参数化查询或预编译语句，把搜索词作为参数绑定，避免直接拼接 SQL；同时可对输入进行必要校验与转义，限制数据库账户权限，并关闭面向用户的详细数据库报错，以降低注入风险和错误信息泄露。


## 学习总结

本次靶场实验主要学习了：

<br>1. 搜索型注入的验证通常需要先建立正常搜索基线，再抓取请求定位参数，最后在 Repeater 中修改参数并比较返回结果。正常单条结果变为多条用户记录，是判断查询逻辑被改变的重要观察点。
<br>2. 理解 %、OR '1'='1' 和 \# 在搜索型注入中的作用，有助于分析 LIKE 查询中的字符串闭合、恒真条件和注释截断。后续学习可结合源码确认实际 SQL 拼接方式，并重点掌握参数化查询这一根本修复手段。
